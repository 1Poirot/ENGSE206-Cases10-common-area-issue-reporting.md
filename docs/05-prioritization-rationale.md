# 05 — Prioritization Rationale: Common-area-issue-reporting

> ไฟล์นี้อธิบาย “ทำไม” requirement แต่ละข้อจึงได้ priority ตามที่กำหนด เพื่อให้นักศึกษาเห็นว่าการจัดลำดับไม่ใช่การเดาหรือเลือกตามความชอบ

## 1. หลักคิด

ทีมเลือกใช้วิธี MoSCoW โดยมีหลักเกณฑ์การพิจารณาดังนี้:

1. พิจารณาจากความจำเป็นต่อกระบวนการหลักของระบบ 
2. พิจารณาจากคุณค่าต่อผู้ใช้งาน
3. พิจารณาจากผลกระทบหากไม่มี Requirement
4. พิจารณาจาก Dependency กับ Requirement อื่น

โดยแบ่งระดับความสำคัญออกเป็น:

*   **M - Must:** จำเป็นต่อการทำงานหลักของระบบ (ขาดไม่ได้เด็ดขาด)
*   **S - Should:** มีความสำคัญ แต่ระบบยังทำงานหลักได้หากไม่มี (สำคัญแต่ไม่ถึงขั้นวิกฤต)
*   **C - Could:** เพิ่มความสะดวก แต่ไม่จำเป็นต่อระบบหลัก (มีก็ดี ไม่มีก็ได้)
*   **W - Won't:** ยังไม่พัฒนาใน Release ปัจจุบัน (ครั้งนี้ยังไม่ทำ)

## 2. เหตุผลราย requirement

| Req ID | Priority | เหตุผลหลัก | Trade-off / Dependency |
|---|---|---|---|
| FR-01 | Must | จำเป็นต่อการทำงานหลักของระบบ เพื่อให้เจ้าหน้าที่มีข้อมูลเพียงพอสำหรับตรวจสอบและดำเนินการ | ต้องมีการยืนยันข้อมูลขั้นต่ำ (required fields) ที่จำเป็นต่อการรับเรื่อง |
| FR-02 | Must | เพื่อให้ผู้แจ้งสามารถติดตามความคืบหน้าได้อย่างชัดเจน โดยไม่กำหนดกระบวนการเกินข้อมูลที่ยืนยันแล้ว | ต้องมีการยืนยันเหตุการณ์ที่ต้องแจ้งเตือน ช่องทางการแจ้งเตือน และระยะเวลาที่เหมาะสม |
| FR-03 | Should | เพื่อลดปัญหาการแจ้งซ้ำและรักษาข้อมูลของผู้แจ้งแต่ละราย | เกณฑ์การตรวจสอบรายการซ้ำต้องได้รับการยืนยันจากผู้เกี่ยวข้องก่อนนำไปใช้เป็นกฎของระบบ |
| FR-04 | Must | เพื่อให้เหตุที่มีความเสี่ยงได้รับการจัดการอย่างเหมาะสม โดยยังไม่กำหนดเกณฑ์ความเร่งด่วนเอง | ต้องได้รับการยืนยันเกณฑ์การจัดระดับความรุนแรง และบทบาทที่ต้องได้รับการแจ้งเตือนในแต่ละระดับก่อน |
| FR-05, NFR-04 | Must | เพื่อให้สามารถตรวจสอบการดำเนินงานย้อนหลังได้ และผู้ใช้งานทั่วไปต้องไม่สามารถแก้ไขหรือลบข้อมูลนี้ได้ | ต้องยืนยันข้อมูลที่ต้องบันทึก ระยะเวลาการเก็บรักษา และสิทธิ์การเข้าถึง Audit Log |
| FR-06 | Should | เพื่อให้แต่ละรายการมีผู้รับผิดชอบที่ชัดเจน | เกณฑ์การมอบหมายงานหรือการโอนงานต้องได้รับการยืนยันจากผู้เกี่ยวข้องก่อน |
| FR-07 | Should | เพื่อสนับสนุนการติดตามและวิเคราะห์ข้อมูล | ต้องยืนยันรูปแบบรายงาน ตัวกรองที่จำเป็น และตัวชี้วัดที่ผู้บริหารต้องการ |
| FR-08 | Should | เพื่อสรุปรายงานข้อมูลการแจ้งปัญหา สนับสนุนการติดตามผลและการวางแผนปรับปรุง | ต้องยืนยันรูปแบบรายงาน ข้อมูลต้นทาง และตัวชี้วัดที่ผู้บริหารต้องการ |
| NFR-01 | Must | เพื่อให้ระบบมีขั้นตอนการแจ้งปัญหาที่เข้าใจง่าย และลดความซับซ้อนในการใช้งาน | ผู้ใช้งานต้องสามารถแจ้งปัญหาพร้อมข้อมูลที่จำเป็นได้ภายในขั้นตอนเดียว |
| NFR-02 | Must | เพื่อควบคุมการเข้าถึงข้อมูลและการดำเนินงานตามหน้าที่ | ต้องจัดทำ Role Matrix และตรวจสอบสิทธิ์ของแต่ละบทบาท |
| NFR-03 | Must | เพื่อรักษาความถูกต้องและครบถ้วนของข้อมูลเมื่อมีการเปลี่ยนสถานะ มอบหมายงาน หรือรวมรายการ | ต้องออกแบบระบบให้ข้อมูลเดิมและประวัติต้องไม่สูญหาย |
| ISSUE-01 | Won't yet | ระบบซ่อมบำรุงเชิงลึก ระบบบริหารครุภัณฑ์ และระบบจัดซื้อ ถูกจัดให้อยู่นอกเหนือขอบเขตการทำงาน (Out of Scope) | ใช้เป็นข้อจำกัดขอบเขต (Boundary) ไม่ใช่ Requirement ของการแจ้งปัญหา |
| ISSUE-02 | Won't yet | ยังไม่ควรกำหนดเทคโนโลยี ช่องทางแจ้งเตือน (เช่น LINE, QR) หรือรายละเอียด UI ในตอนนี้ | ต้องรอให้มีหลักฐาน (evidence) ยืนยันก่อนนำมาใช้ ไม่ควรเดาไปเอง |

## 3. สิ่งที่ไม่ได้เลือกเป็น requirement ทันที

| สิ่งที่พบใน Week04 | เหตุผลที่ยังไม่กำหนดเป็น requirement |
|---|---|
| ระบบซ่อมบำรุงเชิงลึกและการบริหารครุภัณฑ์ | ระบบนี้ถูกจัดให้อยู่นอกเหนือขอบเขตการทำงาน (Out of Scope) |
| ระบบจัดซื้อวัสดุหรืออุปกรณ์ | ระบบจัดซื้อถูกจัดให้อยู่นอกเหนือขอบเขตการทำงาน (Out of Scope) |
| การแจ้งเหตุฉุกเฉินที่ต้องประสานงานกับหน่วยงานภายนอก | กิจกรรมนี้ถูกจัดให้อยู่นอกเหนือขอบเขตการทำงาน (Out of Scope) |
| การฟันธงใช้ LINE, QR, photo, framework หรือ database | ยังไม่ควรกำหนดเทคโนโลยี ช่องทางแจ้งเตือน หรือรายละเอียด UI หากยังไม่มีหลักฐาน (evidence) ยืนยัน |
| การกำหนดเกณฑ์ความเร่งด่วนจากสมมติฐานของทีม | เกณฑ์การจัดระดับความเร่งด่วนต้องได้รับการยืนยันจากผู้เกี่ยวข้องก่อนนำไปใช้เป็นกฎของระบบ (BR-10) |

## 4. บทเรียนสำหรับนักศึกษา

- Priority สูงไม่ได้แปลว่ารายละเอียดครบแล้วเสมอไป
- Requirement ที่สำคัญแต่ยังขาด policy อาจเป็น `Needs Follow-up` เช่น การตรวจจับรายการซ้ำ (FR-03) และการจำแนกความเร่งด่วน (FR-04) ที่ยังต้องรอผู้เกี่ยวข้องยืนยันเกณฑ์ให้ชัดเจนเสียก่อน
- Issue ที่สำคัญมากอาจต้องเป็น `Hold` หากยังไม่มี evidence มารองรับ เช่น การมอบหมายงาน (FR-06) ที่ยังต้องรอยืนยันหลักเกณฑ์การมอบหมายและผู้มีอำนาจก่อน
- Backlog ที่ดีช่วยบอกว่า “ทำอะไรต่อได้” และ “อะไรยังไม่ควรเดา”
